# rtauto_sop

**작업자 행동인식 기반 SOP 준수 지원 시스템** — AI 모델 학습/검증 저장소

알티자동화(RT Automation)의 시범 과제입니다. 이 저장소는 전체 시스템 중 **객체 검출 모델을
준비·검증하는 파트**만 담고 있습니다.

**현재 진행**: **감시단원 카메라가 담당하는 판정 항목 3개**(N인 1조 인원 수 / 보호구 착용 /
안전구역 침범)를 하나의 통합 데모(`webcam_sop.py`)로 구현 완료. 위반 발생 시 실제 브라우저
푸시 알림까지 가는 경로도 프로토타입으로 검증했습니다. 작업자 카메라가 담당하는 항목
(항목·순서, 급소포인트)은 **세정기 SOP 문서가 선행 조건**이라 착수 전입니다.

---

## 1. 시스템 개요

작업자 2인 1조 작업을 카메라로 검출해 엣지 PC가 SOP(표준작업절차)와 대조하고, 편차가
확정되면 작업자에게는 헤드셋 음성으로, 관리자에게는 휴대폰 알림으로 즉시 통보합니다.

- **시범 대상**: 세정기 작업
- **카메라 구성**: 현장 고정이 아닌 **착용형(체스트 마운트)**. 실제 작업자 1인 + 안전감시단원
  1인이 각각 바디캠을 착용(총 2대). 설비 형상·위치가 바뀌어도 같은 구성을 그대로 사용.
- **처리 위치**: 영상·음성 모두 현장 엣지 PC 1대에서 처리. 사무실 서버·관제 PC 없음.
  인터넷 회선 1개만 있으면 동작하며, 인터넷이 끊겨도 현장 경보는 계속 울림.

### 감지 항목

본사 SOP 양식에서 다음 4가지를 검출 대상으로 정의합니다.

| SOP 문서 항목 | 시스템 판정 항목 | 주 검출 경로 | 구현 |
|---|---|---|---|
| 안전관리대책 | 2인 1조 인원 수 | 감시단원 바디캠 (2~4m) | ✅ |
| 안전관리대책 | 보호구 착용 | 감시단원 바디캠 (2~4m) | ✅ |
| 위험요인 | 안전구역 침범 | 감시단원 바디캠 (광역 시점) | ✅ PoC |
| 위험요인 | 위험 자세(사다리 끝단) | 감시단원 바디캠 (광역 시점) | — |
| 항목·순서 | 단계 순서 위반 · 단계 누락 | 작업자 바디캠 (근접 시점) | SOP 필요 |
| 급소포인트 | 필수 동작 누락 · 확인 절차 생략 | 작업자 바디캠 (0.8m 이내) | SOP 필요 |
| STEP별 작업시간 | 표준 소요시간 초과 · 과속 진행 | 양 카메라 공통 (체류시간) | SOP 필요 |

카메라 2대는 **거리가 달라 담당 항목이 갈립니다.** 현재 구현된 3개는 전부 감시단원 카메라
항목이고, 작업자 카메라 채널은 아직 코드가 없습니다. 두 채널은 각자 판정한 뒤 SOP 상태
기계에서 합쳐지는 구조가 될 예정입니다.

## 2. AI의 역할

**AI는 객체 검출 · 추적 · 음성 인식(STT)에만 사용합니다.** 편차 판정과 응답 문구는 규칙
기반으로 처리하여, 판정 근거를 사람이 그대로 추적할 수 있게 합니다.

- 사람 · 안전보호구 같은 범용 객체는 **공개 사전학습 모델을 그대로 사용**하는 것이 기본
  방침입니다(별도 학습 비용 없음).
- 세정기 특유의 부품이나 급소포인트 동작처럼 공개 모델이 다루지 않는 항목만, 소량의 현장
  영상으로 미세조정(fine-tuning)합니다. 항목별 필요 여부는 1주차 현장 실측에서 확정합니다.
- **이 저장소의 헬멧 검출 실험**은 위 "보호구 착용" 항목이 공개 데이터/모델로 어느 정도
  커버되는지 사전 검증하는 작업입니다. → 아래 6절 결과 참고.

### AI 처리 흐름 (영상 경로)

```
① 스트림 수신(RTSP/H.264, FFmpeg 3fps)                    ← 웹캠으로 대체 중 (장비 입고 후 RTSP)
② 객체 검출 (YOLO 계열 1-stage: 사람·안전모·장갑 …)        ← 완료 (person, 안전모)
③ 추적·좌표화 (ByteTrack, 중복 제거, 구역 좌표 매핑)        ← 완료 (ByteTrack + ArUco 구역 매핑)
④ 상태 집계 (인원 수·보호구·구역 체류·자세, 3초 창 다수결)  ← 완료 (감시단원 채널 3항목)
⑤ SOP 대조 (구조화된 SOP와 STEP 순서·표준시간 규칙 비교)    ← SOP 문서가 없어 착수 전  ← 다음 관문
⑥ 편차 확정 (중대/주의/정상 등급 산정 → 출력 라우팅)        ← 규칙 단위는 동작, 등급 차등은 미구현
```

출력 경로는 Web Push 알림까지 프로토타입으로 연결돼 있습니다(6절). 헤드셋 음성(TTS)과
이력·클립 저장은 미착수입니다.

음성 경로는 헤드셋 PTT 버튼 입력 시에만 채널이 열리며(상시 녹음 아님), `faster-whisper`로
STT 후 키워드 규칙으로 의도를 분류해 SOP를 조회하고 TTS로 응답합니다.

## 3. 세정기 SOP 표준 문서

시스템의 판정 기준은 SOP를 구조화한 데이터입니다. 자사 SOP에 세정기 작업이 없어, 이번
과제에서 「세정기 작업 표준 문서(SOP)」를 직접 제작합니다.

현장 관찰·영상 촬영 → 작업 단계 분해 → 표준 소요시간 측정 → 급소포인트·위험요인 도출 →
현장 검토·승인 → 승인 문서를 JSON으로 변환해 판정 엔진에 적재. 산출물이 문서와 시스템
양쪽에 남고, 다른 설비로 확장할 때는 같은 양식의 SOP를 JSON으로 바꿔 끼우면 됩니다.

## 4. 데이터 흐름 (전송 구간)

| 구간 | 데이터 | 매체 | 규격 | 지연 목표 |
|---|---|---|---|---|
| ① 바디캠 → 엣지 PC | 영상 2채널 | WiFi 5GHz (SoftAP 직결, 인터넷 미경유) | RTSP / H.264 · 1080p 15fps · 대당 ~4 Mbps | 0.5초 이내 |
| ② 헤드셋 ↔ 엣지 PC | 음성 질의/경보 | Bluetooth 5.x (USB 동글) | HFP 양방향 · 16kHz 모노 · 버튼 입력 시에만 개방 | 0.3초 이내 |
| ③ 엣지 PC → 관리자 휴대폰 | 편차 알림·클립 링크 | 인터넷 (유선 랜) | HTTPS + Web Push · 미확인 시 30초 간격 재발송 | 1초 이내 |

- 영상 경로(①)와 알림 경로(③)는 **물리적으로 분리**되어, 인터넷이 끊겨도 영상 수신과 현장
  경보는 그대로 동작합니다.
- 무선 특성상 순간 끊김이 생길 수 있어, **끊긴 구간은 "위반 없음"이 아니라 "판정 보류"**로
  이력에 남깁니다. 각 연결은 1초 주기 heartbeat로 확인하고 3회 연속 미수신 시 단절로 판정합니다.

## 5. 관리자 알림

전용 앱 없이 표준 **Web Push**를 사용합니다(Android/iOS 구성 동일). 엣지 PC가 알림
수신용 웹페이지를 제공하고, 관리자가 홈 화면에 한 번 추가 후 알림을 허용하면 끝입니다.

놓침 방지 3단계: ① 잠금화면 푸시에서 색·문구로 중대 편차 구분 → ② 탭하면 전체화면 경보
(경보음·진동 반복) → ③ 확인 버튼 누를 때까지 30초 간격 재발송.

> iOS는 16.4 이상에서 홈 화면 추가 시에만 Web Push가 동작하며, 잠금화면 알림음은 OS
> 기본음으로 고정됩니다.

> **업데이트(2026-09-15)**: 위는 기획안 원안(전용 앱 없이 Web Push)이고, 실제로는 관리자 폰용
> **전용 Android 앱**을 별도로 제작해 진행 중입니다 — [rtauto_sop_android](https://github.com/minha8680/rtauto_sop_android)
> ("RT SOP 알림"). FCM data-only 메시지를 받아 알림+진동+알람음+TTS로 재생하는 수신 전용 앱이고,
> 편차 판정은 여전히 이 저장소(엣지 PC 역할)가 담당합니다. 이 저장소의 `push_server.py`(Web Push)는
> 초기 프로토타입으로 남겨두고, 실제 발송은 `send_test_alert.py`(FCM)로 전환 중입니다.
> **`send_test_alert.py` → 실제 휴대폰 알림 수신까지 확인 완료** — Web Push가 막혔던
> HTTPS/MDM 문제를 네이티브 앱 경로로 우회함. **`webcam_sop.py --fcm-token`으로 연결까지
> 완료** — 4규칙 위반이 실제로 확정될 때마다 자동으로 폰에 알림이 간다(등급도 함께 전달).
> 단, `rtauto_sop_android`는 **Android 전용**이라 iOS 관리자가 생기면 못 씀 — 그래서
> `push_server.py`(Web Push, Android/iOS 공통)는 지우지 않고 iOS용 대안 경로로 남겨두기로
> 결정(2026-09-15, iOS 지원 여부는 보류 상태).

## 6. 학습 결과 — 안전모 착용/미착용 검출

공개 데이터만으로 "보호구 착용" 항목을 판정할 수 있는지 검증한 실험입니다.

| | helmet_v1 | **helmet_v2** |
|---|---|---|
| 데이터셋 | `hard-hat-detection-ws2wk` (668장, 착용 위주) | `joseph-nelson/hard-hat-workers` (~7,000장) |
| 클래스 | hard hat / no hard hat / not hard hat | helmet / no_helmet (person 제외) |
| 미착용 학습 표본 | 16 ~ 64 인스턴스 | 1,000+ 인스턴스 |
| mAP@50 | 0.41 | **0.96** |
| 착용 검출률 (recall) | 0.91 | **0.97** |
| **미착용 검출률 (recall)** | **0.00 ~ 0.33** | **0.95** |

- helmet_v1과 v2는 **학습 설정이 동일**하고 데이터셋만 다릅니다. 미착용 표본을 늘리자 미착용
  검출률이 0 → 0.95로 올랐습니다. → **성능 한계는 학습량이 아니라 데이터에 있었음**을 확인.
- 이 시스템의 핵심 판정 대상인 **보호구 미착용(SOP 위반) 검출이 공개 데이터로 가능**함을
  확인했습니다. 단, 현장 조건(바디캠 화각·거리·조도)에서의 성능은 1주차 실측으로 별도 검증 필요.
- 상세: [`docs/helmet_v1/metrics.md`](docs/helmet_v1/metrics.md), [`docs/helmet_v2/metrics.md`](docs/helmet_v2/metrics.md),
  [`docs/helmet_v2/webcam_test.md`](docs/helmet_v2/webcam_test.md)

가중치 파일(`*.pt`)은 용량 문제로 저장소에 포함하지 않습니다 (로컬 `models/` · Google Drive 보관).

### 학습 결과 — 보안경 착용/미착용 검출 (glasses_v1 → v2 → v3)

helmet과 같은 "보호구 착용" 항목의 두 번째 대상입니다. 두 번의 재학습을 거쳤습니다 — 매번
"지표는 좋은데 실물에서 실패"하는 다른 종류의 문제가 나왔고, 그때마다 원인을 좁혀서
데이터셋/라벨링을 고쳤습니다.

1. **glasses_v1**: 학습 전 클래스 균형 확인(Goggles 4,188:NO-Goggles 4,092, 약 1:1)하고
   시작해 지표상으로는 성공했지만, **실물 검증에서 완전히 실패**했습니다 — 실제 사용 중인
   풀페이스 단일렌즈형 보안고글이 실물로도 프린트로도 전혀 인식되지 않았습니다(conf 0.01까지
   낮춰도 0건). 데이터셋 클래스명이 "Goggles"였음에도 실제 이미지가 안경형 위주였던 것으로
   추정됩니다.
2. **glasses_v2**: 다른 데이터셋(`seafty_goggles`)으로 재학습 — 이번엔 클래스명만 보지 않고
   (1) Roboflow API로 정확한 인스턴스 수 조회 (2) 여러 후보가 사실은 같은 원본 데이터인지
   확인 (3) 대표 이미지로 실제 스타일 확인, 세 단계를 거쳐 골랐습니다. 풀페이스 고글 인식은
   해결됐지만, **1m 거리의 일반 안경을 confidence 0.6으로 "고글"이라고 오탐**하는 새 문제가
   실제 웹캠 사용 중 발견됐습니다. 원본 데이터셋의 3번째 클래스 `spec`(일반 안경)을 배경으로
   드롭해서, 모델이 "이건 고글이 아니다"라는 대조 신호를 못 받은 게 원인이었습니다.
3. **glasses_v3**: `spec`을 배경이 아니라 **`no_goggles`로 재매핑**해서 재학습 — "일반 안경
   착용"과 "미착용"은 SOP 판정상 둘 다 "안전고글 미착용"이라는 같은 결론이라 의미상으로도
   맞는 매핑입니다. `glasses_v2_best.pt`에서 warm start해서 30 epoch만에 v2보다 더 나은
   지표에 도달했습니다.

| 지표 | glasses_v1 | glasses_v2 | **glasses_v3** |
|---|---|---|---|
| 데이터셋 | PPE Combined Model 44,002장 중 Goggles/NO-Goggles | seafty_goggles 9,149장 중 goggles/no_goggles (spec 드롭) | seafty_goggles, spec을 no_goggles로 재매핑 |
| mAP@50 | 0.97 | 0.97 | **0.97** |
| 착용 검출률 (recall) | 0.98 | 0.97 | **0.98** |
| 미착용 검출률 (recall) | 0.95 | 0.94 | **0.96** |
| 실물 풀페이스 고글 검증 | 실패 (0건) | 성공 (goggles 0.41) | **성공, confidence 상승 (goggles 0.78)** |
| 1m~4m 거리 일반 안경 오탐 | (검증 안 함) | **실패 (1m, 고글 오탐 0.6)** | **여전히 실패 (2~4m) — 아래 참고** |

- 상세: [`docs/glasses_v1/metrics.md`](docs/glasses_v1/metrics.md), [`docs/glasses_v2/metrics.md`](docs/glasses_v2/metrics.md), [`docs/glasses_v3/metrics.md`](docs/glasses_v3/metrics.md)
- **`webcam_sop.py`(감시단원 채널 통합 데모)에 glasses_v3로 통합 완료(2026-09-18)** — helmet과
  완전히 독립된 규칙으로 추가했다(헬멧·보안경 둘 중 하나만 미착용해도 각각 별도로 위반 확정/알림).
  `webcam_glasses.py`도 glasses_v3로 전환, 문제 분리용 단독 테스트 스크립트로 계속 남겨둠.
- glasses_v2부터는 Colab 세션이 끊겨도 이어서 학습할 수 있도록 Google Drive에 직접
  체크포인트를 저장(`save_period=10`)하고 재실행 시 `resume=True`로 자동 이어받는 방식을
  도입했습니다. glasses_v3는 여기서 한 걸음 더 나아가, 처음부터(`yolov8n.pt`) 다시 학습하는
  대신 이전 버전 가중치에서 warm start하는 방식을 함께 썼습니다.

**2~4m 원거리 오탐은 파이프라인 조정으로 해결 안 됨(2026-09-18)** — glasses_v3로도 2m 이상
거리에서는 일반 안경을 고글로 오인식했습니다. 추론 해상도 상향, 사람 박스 crop, 웹캠 캡처
해상도를 640x480→1920x1080으로 올리는 것(같은 거리에서 얼굴 픽셀 높이가 57px→131px로
실측 증가했음에도), 머리 영역만 좁혀 crop하는 방법까지 순서대로 시도했지만 전부 근본
해결에 실패했고, 오히려 헬멧 판정이 불안정해지는 부작용만 생겨 **전부 되돌렸습니다**
(`webcam_sop.py`/`webcam_glasses.py`는 glasses_v3 모델 전환만 남기고 리셋). 웹캠 자체의
화질·압축·오토포커스 특성이 학습 데이터와 다른 도메인 격차로 보이며, 지금 쓰는 노트북
웹캠은 실제 배치 예정 카메라(포팩트 LIVE ST20, 2K)와 다른 장비라 여기서 더 튜닝해도 실제
하드웨어에서 재현될지 알 수 없어 **바디캠 입고 후 재검증하기로 하고 보류**했습니다. 당장
2m 이상 거리에서 신뢰도가 필요하면 `--no-glasses`로 보안경 판정만 끄고 쓸 수 있습니다.

### 학습 결과 — 장갑 착용/미착용 검출 (glove_v1, 베이스라인)

헬멧·보안경과 달리 **작업자 바디캠(0.8m 이내 근접)** 담당 항목입니다. 세정기 현장을 아직
방문하지 못해 실제 사용 장갑·공구 영상이 없는 상태라, 공개 데이터셋으로 먼저 베이스라인을
잡아뒀습니다.

| 지표 | 값 |
|---|---|
| 데이터셋 | `safety-gloves-xbnf8` v5, 10,459장 (Gloves 4,669 : NO-Gloves 6,135, CC BY 4.0) |
| mAP@50 | 0.933 |
| 착용 검출률 (recall) | 0.930 |
| 미착용 검출률 (recall) | 0.903 |
| 실물 검증 | **완전 실패**(2026-09-21, 아래 참고) |

- 상세: [`docs/glove_v1/metrics.md`](docs/glove_v1/metrics.md)
- helmet_v2(0.96)·glasses_v3(0.974)보다 mAP50이 낮은데, 셋 다 같은 YOLOv8n fine-tuning·
  같은 2클래스 구조인 걸 감안하면 **판정 대상의 형태 가변성 차이**로 보입니다 — 헬멧·고글은
  형태가 비교적 고정적인 반면 장갑을 낀 손은 각도·쥐는 자세·가림에 따라 형태가 크게
  바뀝니다.
- **`webcam_sop.py`에는 통합하지 않습니다.** 장갑은 감시단원 채널이 아니라 작업자 채널
  담당인데, 작업자 채널 처리기 자체가 아직 없기 때문입니다(SOP 문서가 선행 조건). 단독
  검증용으로 `webcam_glove.py`를 뒀습니다.
- **실물 검증에서 우려가 그대로 확인됐습니다.** 화학물질 취급용 안전장갑 실물 사진 7장으로
  테스트한 결과 **6장이 실패**(미검출 또는 완전 미검출)했고, 사람이 실제 착용한 사진 2장은
  **엉뚱한 부위(방호복)를 확신 있게(0.27~0.46) "미착용"으로 오탐**했습니다 —
  `glasses_v2`가 일반 안경을 0.6으로 오탐했던 것과 같은 종류의 결함입니다.
- **대체 공개 데이터셋도 로보플로우 밖까지 확인했지만 전부 불채택했습니다.** Roboflow엔
  "화학장갑" 전용 데이터셋 자체가 없고, SH17은 라이선스가 CC BY-NC-SA(비상업적 전용)라
  이 프로젝트가 지켜온 상업 이용 무제한 원칙에 어긋나 제외했으며, Google Open Images V7의
  "Glove" 클래스(CC BY 4.0)는 라이선스는 맞지만 실제 샘플 40장을 직접 받아 확인한 결과
  화학장갑 스타일이 하나도 없었습니다(전부 겨울·스포츠·전술 장갑). **공개 데이터셋 경로는
  닫혔고, 세정기 현장 영상으로 fine-tuning하는 것 외에 다른 길이 안 보입니다.**

### 웹캠 테스트에서 확인한 것

로컬 웹캠 근접 조건에서 helmet_v2는 착용/미착용을 신뢰도 있게 구분합니다(confidence 0.7~0.9).
다만 다음은 다음 단계 설계에 반영해야 합니다.

- **"helmet 검출 = 착용"이 아님** — 손에 든 헬멧도 `helmet`으로 잡힘. 실제 착용 판정은
  person/head 박스와 helmet 박스의 공간 관계(겹침)로 규칙 단계에서 처리해야 함.
- **가림에 취약** — 얼굴이 가려지면 인물 자체가 미검출 → "위반 없음"이 아니라 판정 보류 처리.
- **원거리 소형 객체(2~4m, 안전모 22~35px) 성능은 미검증** — 바디캠 입고 후 현장 실측 대상.

### 통합 데모 — 감시단원 채널 4규칙 (`webcam_sop.py`)

person 검출+추적, helmet_v2, glasses_v3, ArUco 구역 인식을 한 루프에서 결합했습니다. 규칙
4개 모두 **지속 시간을 채워야 확정되고, 정상 복귀도 지속돼야 해제**되는 방식(기획안 5.6절)입니다.

| 규칙 | 조건 | 기본 지속시간 |
|---|---|---|
| N인 1조 | 인원 수 ≠ N | 3초 |
| 헬멧 미착용 | 특정 인물이 미착용 상태 | 10초 |
| 보안경 미착용 | 헬멧과 완전히 독립적으로 동일하게 판정 | 10초 |
| 안전구역 침범 | 특정 인물의 발 위치가 구역 안 | 3초 |

두 가지 설계 원칙이 들어가 있습니다.

- **"보호구 박스가 보이면 착용"이 아님** — person 박스 안에 helmet(또는 glasses) 박스의
  중심점이 들어오는지로 실제 착용 여부를 판정합니다(`match_ppe_to_persons`, 헬멧·보안경
  공유). 손에 든 헬멧이 착용으로 오판되던 문제를 해결했습니다.
- **모르면 위반도 정상도 아님(판정 보류)** — 보호구 박스를 못 찾은 사람, 구역 마커가 안 보이는
  구간은 "미확인"으로 두고 위반 처리하지 않습니다. 사람 검출 자체가 순간 끊겨도(occlusion)
  마지막 위반 상태를 그대로 이어가며, `--*-clear` 하이스터리시스를 건너뛰고 즉시 해제로
  오판하지 않습니다(`carry_forward_violations`, 2026-09-17).

필요 인원 수(2/3/4인 1조 등)와 지속시간은 코드 수정 없이 실행 인자로 바꿉니다:
```bash
python webcam_sop.py --crew 3 --crew-hold 5 --helmet-hold 15 --glasses-hold 15 --zone-hold 5
python webcam_sop.py --no-zone          # 마커를 준비 못 했을 때 안전구역만 끄기
python webcam_sop.py --no-glasses       # glasses_v3 모델 없이 헬멧만 판정
python webcam_sop.py --source rtsp://<카메라IP>:<포트>/<경로>   # 웹캠 대신 실제 바디캠
```

**바디캠(RTSP)으로 바꿀 때 검출 로직은 그대로입니다.** `_run()`이 `cap.read()`로 나온 이미지
(`frame`)만 받아서 동작하고 그 출처는 전혀 모르는 구조라, 실제로 바뀌는 건 `--source` 인자
하나뿐입니다(`video_source.py`의 `open_video_source`가 RTSP면 자동으로 `CAP_FFMPEG`+저지연
버퍼를 적용 — `rtsp_test.py`와 이 함수를 공유해서 설정이 두 곳에 따로 남지 않게 함).
다만 이건 "실행이 되게" 하는 것과 "안정적으로 계속 돌게" 하는 건 다른 문제입니다 — 끊김
재연결 로직은 지금 `rtsp_test.py`에만 있고 `webcam_sop.py`엔 아직 없고, 작업자캠+감시단원캠
**2채널을 동시에** 받는 구조도 아직 없습니다(지금은 `cap` 1개만 받는 단일 카메라 전제).
RTSP 주소는 반드시 `rtsp_test.py`로 연결 자체가 끊김 없이 들어오는지 먼저 확인한 뒤에 쓸 것.

장비 입고 후 무엇을 어떤 순서로 확인할지는
[`docs/bodycam_test_guide.md`](docs/bodycam_test_guide.md)에 단계별로 정리해뒀습니다
(연결 → 보안경 2~4m 오탐 재현 여부 → 헬멧 판정 → 배터리 지속시간 → SoftAP 반경 → 마커
인식 거리, 순서대로 리스크가 큰 항목부터).

### 안전구역을 "화면 좌표"가 아닌 "실세계 기준"으로 잡는 법

착용형 카메라는 계속 움직이므로, 화면에 고정 폴리곤을 그려두면 카메라가 돌아가는 순간
그 좌표가 엉뚱한 곳을 가리킵니다. 대신 위험구역 네 모서리에 **ArUco 마커**를 두고 매 프레임
마커 위치로 구역을 다시 계산합니다 — 카메라가 움직여도 마커가 보이는 한 구역이 따라오고,
마커가 안 보이면 판정 보류로 침묵합니다.

바디캠은 호흡·발걸음만으로도 미세하게 흔들려 "이번 프레임에 마커 4개 동시"라는 조건이 쉽게
깨집니다. 그래서 **최근 0.4초 안에 본 적 있는 마커는 그 위치를 그대로 사용**해 순간 미검출을
흡수합니다. 마커 1개가 아예 가려져 3개만 보일 때는 **평행사변형 근사**(사각형 대각선의
중점이 같다는 성질)로 4번째 모서리를 추정해 계속 판정합니다 — `--no-zone-estimate`로 끌 수
있습니다. 화면에서 초록 점 = 실시간 인식, 주황 점 = 최근 기억, **빈 마젠타 원 = 추정치**로
구분됩니다. 마커가 2개 이하로 줄면 추정도 불가능해 판정 보류로 돌아갑니다.

`generate_markers.py`로 마커 4장을 만들어 `markers/`에 저장합니다. 웹캠 수준의 개념 검증은
완료했고, 실전 적용 전 마커 재질(방수)·인식 가능 거리(4~10m)·부착 높이를 현장에서 확정해야
합니다. 평행사변형 근사는 카메라가 정면에 가까울 때 잘 맞는 근사치라 각도가 심하게 기울어진
조건에서의 오차도 실측으로 확인해야 합니다.

### 관리자 알림 프로토타입 (`push_server.py`)

기획안 5.5절의 "전용 앱 없이 표준 Web Push" 구조를 로컬에서 재현했습니다. 브라우저로 구독
페이지에 접속해 알림을 허용하면, 위반이 확정되는 순간 실제 푸시 알림이 도달합니다.

```bash
python generate_vapid_keys.py                    # 최초 1회
uvicorn push_server:app --port 8000              # 터미널 1 → localhost:8000 에서 구독
python webcam_sop.py --push-url http://localhost:8000/notify   # 터미널 2
```

같은 위반이 해제됐다 금방 다시 걸리는 **반복(flapping)** 은 클립 저장만 억제합니다 — 기본
5분 안에 재발하면 클립은 생략하다가 3회째에 클립 저장을 재개하고 알림 문구에 "(N회 반복)"을
덧붙입니다(`--repeat-cooldown-min`, `--repeat-threshold`로 조정). **알림(Push/FCM) 자체는
2026-09-16부터 반복 여부와 무관하게 매번 보냅니다** — 처음엔 알림도 같이 억제했는데, 실사용
중 "해제됐다가 진짜로 다시 위반이면 폰이 다시 울려야 안전하다"는 게 확인돼 정책을 바꿨습니다.
알림 피로는 이제 관리자 앱 쪽(자동 해제 건수 배지, 여러 위반 동시 표시, 알림 그룹 요약)에서
완화합니다. `--push-url`/`--fcm-token` 없이 써도(알림 자체를 안 켜도) 클립 억제는 항상
작동합니다.

위반 확정/해제는 **알림 설정과 무관하게** `events.jsonl`에 항상 기록됩니다(기획안 그림3
"엣지 PC 저장" 대응). `python view_events.py`로 확정↔해제를 짝지어 지속시간까지 보여줍니다.
확정되면 알림은 항상 나가고, 클립은 (반복 억제를 통과했을 때만) 최근 10초 프레임을 `clips/`에
mp4로 저장합니다(그림4 "경보 구간 클립(10초)" 대응, `--clip-sec`/`--no-clip`로 조정).

그래도 프로토타입 수준입니다 — localhost 전용(HTTPS 없음), 구독 정보는 JSON 파일 저장, 클립
저장이 동기 처리라 그동안 프레임이 밀림(실전엔 별도 스레드 필요), 30초 재발송·확인(ACK)·
등급별 차등 발송은 미구현.

### 현재 완성도

**감시단원 카메라가 담당하는 판정 항목 4개**(인원 수 / 헬멧 / 보안경 / 안전구역)와 출력 경로(관리자
알림·이력·클립 저장)까지 동작합니다. 아직 없는 것:

- 작업자 카메라 채널 전체 (항목·순서, 급소포인트) — SOP 문서가 선행 조건
- SOP 규칙 판정 엔진, STEP별 소요시간 — 마찬가지로 SOP 문서 필요
- 2채널 동시 수신, 헤드셋 음성(TTS), 엣지 PC 통합, heartbeat, 위험 자세 검출

바디캠이 입고돼도 "꽂으면 시스템이 도는" 상태가 아닙니다. RTSP 2채널 수신, 현장 거리·조도
기준 재튜닝, 마커 실측, GPU 동시 부하 검증이 별도로 필요합니다. 지금까지 한 작업의 가치는
**알고리즘 리스크를 미리 걷어내고 재사용 가능한 모듈을 확보한 것**입니다.

### 환경

- Windows + Git Bash, Python 가상환경(`venv/`)
- 로컬 GPU는 GTX 1050 Ti(4GB)로 학습엔 약함 → **학습은 Google Colab (T4), 로컬은 추론만**
- 로컬 `torch`는 CPU 빌드. 추론(웹캠)은 CPU로 실시간 충분

```bash
source venv/Scripts/activate                       # 가상환경 활성화
pip install --no-cache-dir -r requirements.txt      # 최초 1회 (또는 새 패키지 추가 후)
```

### 학습 (Google Colab)

1. Colab 새 노트북 → 런타임을 T4 GPU로 설정
2. 이 저장소 clone, `pip install ultralytics roboflow`
3. Colab Secrets(🔑)에 `ROBOFLOW_API_KEY` 등록 후 데이터셋 다운로드
4. data.yaml 경로 수정 + (필요 시) 클래스 재매핑
5. `YOLO("yolov8n.pt").train(data=..., epochs=50, imgsz=640, batch=32, device=0)`
6. `best.pt`, `results.png`, `confusion_matrix.png`, `results.csv` 를 `files.download()` 로 내려받기
7. 로컬 `models/` · `docs/<name>/` 에 배치 후 커밋

### 실행 (로컬)

```bash
# 메인 통합 데모 ('q' 종료)
python generate_markers.py   # 최초 1회 — 마커 4장 생성, 프린트해서 구역 네 모서리에 배치
python webcam_sop.py         # 4규칙 전부. --crew N 등 파라미터는 --help 참고
python webcam_sop.py --no-zone                # 마커 없이 인원수+헬멧+보안경만

# 알림까지 연동하려면 (터미널 2개)
python generate_vapid_keys.py                 # 최초 1회
uvicorn push_server:app --port 8000           # 터미널 1 → 브라우저로 localhost:8000 접속해 구독
python webcam_sop.py --push-url http://localhost:8000/notify   # 터미널 2

# 위반 이력 확인 (--push-url 없어도 항상 기록됨, clips/ 에 mp4도 같이 쌓임)
python view_events.py
python webcam_sop.py --no-clip      # 경보 구간 클립 저장을 끄고 싶으면

# 바디캠(RTSP) 연결 — 먼저 rtsp_test.py로 그 주소가 끊김 없이 들어오는지 확인한 뒤에 쓸 것
python webcam_sop.py --source rtsp://<카메라IP>:<포트>/<경로>

# 단일 기능 검증용 (문제 생겼을 때 원인 분리에 유용)
python webcam_helmet.py     # 안전모만
python webcam_glasses.py    # 보안경만 (glasses_v3)
python webcam_glove.py      # 장갑만 (glove_v1, 베이스라인·실물 검증 완전 실패)
python webcam_person.py     # 인원 수 + 추적만
python webcam_zone.py       # 안전구역만
python debug_aruco.py       # 마커가 인식되는지만 (조명/거리/인쇄 문제 진단)
python predict.py           # test 이미지 폴더 일괄 추론 → runs/ 에 시각화 저장
```

### 파일

| 파일 | 용도 |
|---|---|
| **`webcam_sop.py`** | **메인 통합 데모** — 감시단원 채널 4규칙(N인 1조 + 헬멧 + 보안경 + 안전구역) |
| `push_server.py` | Web Push 알림 프로토타입 서버 (FastAPI, 구독 페이지 + `/notify`) |
| `generate_vapid_keys.py` | Web Push용 VAPID 키 생성 (최초 1회) |
| `send_test_alert.py` | 관리자 폰 전용 앱(rtauto_sop_android)으로 FCM 테스트 발송 — 엣지 PC 대신 |
| `rtsp_test.py` | 바디캠 RTSP 연결·지연·재연결만 검증 (검출 모델 없음). 장비 입고 직후 최우선으로 돌려볼 것 |
| `video_source.py` | 웹캠/RTSP를 여는 공통 함수 — `webcam_sop.py`·`rtsp_test.py`가 공유(중복 코드 방지) |
| `view_events.py` | `events.jsonl`(위반 이력)을 확정↔해제 짝지어 읽기 좋게 출력 |
| `clips/` | 위반 확정 시 자동 저장되는 경보 구간 클립(mp4), gitignore |
| `generate_markers.py`, `markers/` | 안전구역용 ArUco 마커 생성/보관 |
| `trackers/bytetrack_person.yaml` | 저FPS(로컬 CPU)용 ByteTrack 튜닝 설정 |
| `requirements.txt` | 로컬 실행 환경 (학습은 Colab이라 무관) |
| `webcam_helmet.py`, `webcam_glasses.py`, `webcam_glove.py`, `webcam_person.py`, `webcam_zone.py` | 단계별 검증용 단일 기능 스크립트 |
| `debug_aruco.py` | 마커 인식 진단 (코드 문제 vs 조명·거리 문제 분리) |
| `predict.py` | 학습 가중치로 test 이미지 일괄 추론 |
| `docs/helmet_v1/`, `docs/helmet_v2/`, `docs/glasses_v1/`, `docs/glasses_v2/`, `docs/glasses_v3/`, `docs/glove_v1/` | 학습 결과 지표·그래프·웹캠 테스트 평가 |
| `docs/bodycam_test_guide.md` | 포팩트 LIVE ST20 입고 후 테스트 절차 (연결 → 인식 정확도 → 배터리 → 무선망 → 마커) |

> `main.py` 자리는 비워둠 — 작업자/감시단원 2채널을 합친 파이프라인이 생기면 그것이 진입점.
> 데이터셋 다운로드·로컬 학습 스크립트는 없음 — 학습은 전부 Colab에서 진행 (위 절차 참고).
> VAPID 키·구독 정보(`*.pem`, `push_subscriptions.json`)는 저장소에 포함되지 않습니다.

> Roboflow YOLOv8 export의 `data.yaml`은 경로가 잘못돼 있어(`../train/images`) 절대경로
> `path:` 키를 추가해야 학습이 됩니다. `datasets/`는 저장소에 포함되지 않습니다.
