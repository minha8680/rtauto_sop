# 포팩트 LIVE ST20 입고 후 테스트 절차

이 문서는 **1대만 먼저 구매하기로 한 결정**(2026-09-18)에 따라, 그 1대로 무엇을 어떤
순서로 확인해야 2대째 구매 여부를 판단할 수 있는지 정리한 체크리스트다. 순서는
리스크·비용이 큰 것부터 — 앞 단계가 막히면 뒤 단계를 볼 의미가 없다.

**전제**: `webcam_sop.py`는 이미 `--source rtsp://...`로 실장비를 받을 수 있게 돼 있다
(`video_source.py`, 2026-09-18). 검출 로직(헬멧·보안경 인식, 규칙 엔진)은 전혀 안 바뀌고,
영상 입력만 웹캠에서 RTSP로 바뀐다 — 자세한 배경은 README.md "바디캠(RTSP)으로 바꿀 때
검출 로직은 그대로입니다" 단락 참고.

## 0. 시작 전에 확인할 것

- **RTSP 주소**: 카메라 앱/매뉴얼에서 확인. 모르면 흔한 형식을 순서대로 시도:
  `rtsp://<IP>/live`, `rtsp://<IP>:554/stream1`, `rtsp://<IP>/h264`.
  아이디/비번이 필요하면 `rtsp://user:pass@<IP>/...` 형식.
- **SoftAP 연결**: 엣지 PC의 USB WiFi 동글을 SoftAP로 구성해 바디캠이 여기 붙게 한다
  (기획안 5.1절). 카메라의 IP는 이 SoftAP가 할당한 주소.
- **venv 활성화**: `source venv/Scripts/activate`

## 1. RTSP 연결 자체 — 가장 먼저, 검출 모델 없이

```bash
python rtsp_test.py rtsp://<카메라IP>:<포트>/<경로>
```

- 5초마다 실측 FPS · 재연결 횟수 · 끊김 횟수가 콘솔에 찍힌다.
- **통과 기준**: 몇 분 동안 끊김 없이 15fps 근처를 유지한다.
- **실패하면**: 주소/포트, SoftAP 접속 상태, 카메라 전원부터 의심. 여기서 막히면 2번 이후는
  의미가 없다 — 검출 품질을 논할 단계가 아니다.
- 장시간(배터리 테스트와 겸해서) 돌리려면 `--no-display` 추가.

## 2. 보안경 2~4m 오탐 재현 여부 — 최우선 검출 테스트

가장 결과가 갈리는 항목이다. 노트북 웹캠에서 이미 확인된 문제(2~4m에서 일반 안경을
보안경으로 오인식, `docs/glasses_v3/metrics.md` 참고)가 실제 카메라에서도 재현되는지 여기서
결론 난다.

```bash
python webcam_sop.py --source rtsp://<카메라IP>:<포트>/<경로> --no-zone --crew 1
```

(마커·2인 조건은 아직 준비 안 됐을 수 있으니 `--no-zone --crew 1`로 보안경·헬멧 판정에만
집중)

- 2m · 3m · 4m 각 거리에서 순서대로 확인: **일반 안경 / 실물 보안경 / 미착용** 세 경우.
- 화면에 표시되는 confidence와 판정(착용/미착용)을 거리·상황별로 기록.
- **통과 기준**: 2~4m에서 일반 안경이 "보안경 착용"으로 안 뜬다.
- **재현되면**: 그 영상을 수백 장 뽑아 소량 fine-tuning, 또는 보안경 판정 유효거리를 2m
  이내로 제한(`docs/glasses_v3/metrics.md` "다음 단계" 참고). 당장 급하면 `--no-glasses`로
  보안경 판정만 끄고 헬멧+구역으로 운용 가능.
- **재현 안 되면**: 노트북 웹캠과 실제 배치 카메라의 화질·압축 차이가 원인이었다는 뜻 —
  그대로 사용.

## 3. 헬멧 2~4m 판정

같은 자리에서 헬멧 착용/미착용을 반복 확인.

- **통과 기준**: 공개 데이터 기준 지표(mAP50 0.96, `docs/helmet_v2/metrics.md`)와 크게
  다르지 않은 confidence로 안정적으로 구분됨.
- **애매하면**: `--helmet-hold`/`--helmet-clear`나 `HELMET_CONF`(웹캠_sop.py 상단 상수) 조정
  필요성을 기록해둘 것 — 지금 당장 코드를 고치기보다는 얼마나 벗어났는지부터 기록.

## 4. WiFi(SoftAP) 송출 배터리 지속시간

기획안 표4에 "RTSP 송출 약 5.5시간"은 **LTE 기준**으로만 공표돼 있고, 실제로 쓰는 WiFi
송출 지속시간은 미공개다.

```bash
python rtsp_test.py rtsp://<카메라IP>:<포트>/<경로> --no-display
```

카메라를 완전 충전한 뒤 켜두고, 방전(연결 끊김이 재연결 안 되는 시점)까지 걸린 시간을 잰다.

- **통과 기준**: 8시간 근무를 예비 배터리 1개 교체로 커버 가능한 수준(기획안 표4 대응
  방안).
- **실패하면**: 예비 배터리 추가 구매 또는 교체 주기 단축 필요.

## 5. SoftAP 무선망 반경

기획안 표4는 "5GHz 반경 약 15m(실내 개활 기준), 금속 설비 차폐 시 각 절반으로 감소"라고
적혀 있다. 실제 값을 잰다.

- 엣지 PC(SoftAP)에서 점점 멀어지며 `rtsp_test.py`의 끊김 횟수·재연결 횟수를 관찰.
- 가능하면 금속 설비 근처(세정기 환경과 비슷한 곳)에서도 반복.
- **기록할 것**: 안정적으로 유지되는 최대 반경(개활 기준 / 금속 근처 기준 각각).

## 6. 안전구역 마커(ArUco) 인식 거리

`generate_markers.py`로 만든 마커를 4~10m 거리에 두고 인식되는지 확인.

```bash
python debug_aruco.py    # 마커 인식 자체만 진단 (조명/거리/인쇄 문제 분리)
```

이후 실제 판정까지 보려면:

```bash
python webcam_sop.py --source rtsp://<카메라IP>:<포트>/<경로>
```

- **통과 기준**: 프린트한 마커가 그 거리에서 인식됨.
- **실패하면**: 마커 크기·재질 재설계 필요(`docs/glasses_v2/metrics.md`가 아니라 기획안
  5.7절 "실전 적용 전 확인할 것" 항목 참고).

## 2대째 구매 결정 게이트

1~2번이 사실상 게이트다.

- **1번(RTSP 연결)과 2번(보안경 오탐 재현 안 됨)을 통과** → 2대째 구매 진행, 이후 2채널 동시
  수신 구조 개발 착수.
- **1번에서 막힘** → 코드/네트워크 문제부터 해결, 2대째는 보류.
- **2번에서 오탐 재현됨** → fine-tuning 또는 유효거리 제한을 먼저 적용해보고, 그 결과를 보고
  2대째를 결정(모델 문제라 카메라를 한 대 더 사도 안 풀릴 가능성이 있음).
